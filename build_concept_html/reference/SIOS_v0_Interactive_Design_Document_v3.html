01 · What we decided

Scope the first version aggressively.

FROZEN

Fedora stays underneath

Reuse Linux processes, filesystem, drivers, desktop, apps, Wayland, and cgroups.

FROZEN

Goals sit above processes

GoalProcess tracks the outcome; Linux processes are temporary executors.

FROZEN

Use atomic capabilities

Expose folder.open, file.open, app.launch, file.move, and similar typed operations.

FROZEN

Verify every result

An operation only completes when SIOS observes the intended system state.

FROZEN

Input is interchangeable

Mouse, hand tracking, keyboard, push-to-talk voice, and future inputs share one normalized interface.

EXPERIMENTAL

Reasoning stays optional

v0 can be mostly deterministic. AI models plug in later where ambiguity exists.

The infrastructure around intelligence.

SIOS should not compete mainly by owning the smartest model. Its durable layer is the control substrate around models: context, authority, execution, verification, observability, and trusted capability distribution.

Security Engine · AI-IAM

How authority should actually look and feel in SIOS.

The security experience should not look like a traditional Linux permissions dialog copied onto an AI system. SIOS needs a new IAM model where humans, GoalProcesses, local models, external agents, capabilities, and services are all explicit principals, and authority is granted as narrow, expiring leases tied to a purpose.

Core security rule: identity answers who/what is acting; role answers what kind of actor it is; policy answers what it may request; a GoalProcess lease answers what it may actually do right now.

10. Security decisions we should freeze

DecisionSIOS positionWhy
Can a model hold broad user permissions?No.Reasoners propose actions; they do not inherit the human’s full account authority.
Who receives execution authority?The GoalProcess.Authority stays tied to a concrete purpose and lifetime.
How long should authority last?Shortest practical lease.One action, N uses, or goal completion.
Can installed MCPs act whenever they want?No.Installation makes capabilities available; it does not authorize execution.
Can child goals gain more authority?No by default.Delegated authority must be equal to or narrower than the parent lease.
Should secrets be shown to models?No.A broker injects credentials directly into trusted transports.
How are risky actions handled?ASK / sandbox / deny.Risk policy determines whether the human must approve.
What happens when a goal ends?Leases revoke automatically.No lingering agent permissions.

11. Honest open problems

  • Policy language: we still need to decide whether SIOS uses a custom policy DSL, a Rego/Cedar-like engine, or another formal representation.
  • Identity federation: local single-user identity is straightforward; organizations, shared devices, delegated corporate identity, and external agent identity are harder.
  • TOCTOU: permission may be valid when checked but the world can change before execution; high-risk actions need atomic or revalidated execution.
  • Composite actions: a harmless-looking goal can become risky through a chain of individually allowed operations.
  • Provider trust: even a correctly authorized MCP can behave maliciously or leak data; authority alone does not replace sandboxing and verification.
  • Usability: too many approval prompts will destroy the product. SIOS needs progressive trust, sensible defaults, and risk-based prompting without silently granting broad access.

09 · The “underground tunnel” idea

SIOS should control the computer through structured system paths, not by pretending to be a human.

The phrase “underground tunnel” means that SIOS should prefer a machine-readable control path underneath the visible user interface. Traditional computer-use agents often inspect pixels, move a cursor, click buttons, wait for animations, and visually confirm the result. That works, but it is slow and fragile. SIOS should instead expose direct typed capabilities whenever the operating system or application provides one.

This does not mean SIOS never uses the visible UI. UI control remains a compatibility layer for software that exposes no reliable machine interface. The architectural rule is: 

1. Native SIOS capability
2. OS / application API
3. Trusted MCP capability
4. Accessibility / semantic UI interface
5. Pixel + pointer automation only as fallback

This hierarchy is important because it turns “AI operating the computer” into “the computer exposing a better interface to intelligence.” That is a core SIOS design thesis.

10 · SIOS MCP / Capability Store

MCP servers become installable capabilities inside SIOS.

SIOS should include an in-house registry and store experience that can ingest listings from the official MCP Registry, evaluate them against SIOS policy, and expose approved servers as installable “apps” or capabilities. The user should not need to manually edit configuration files or understand MCP transports.

What “install” should mean

1. Discover
SIOS syncs MCP metadata from the official registry and displays compatible capabilities.
2. Inspect
SIOS shows publisher, requested permissions, transport, data access, authentication, and risk.
3. Install / Connect
Local servers are installed into a managed sandbox; remote servers are connected through a managed transport.
4. Authenticate
OAuth/API credentials are stored through a SIOS secret broker rather than handed directly to arbitrary models.
5. Translate
MCP tools are normalized into the same SIOS capability vocabulary used by native system actions.
6. Authorize per goal
Installing an app does not give every GoalProcess permanent access to it.

We should not blindly mirror every MCP and make it one-click executable. A public registry is a discovery source, not a security boundary. SIOS must validate packages/endpoints, declare permissions before connection, isolate local servers, protect credentials, and allow revocation.

12 · Build order

Build one vertical slice first

  1. Input adapter: connect hand tracking and normal mouse to one interface.
  2. GoalProcess record: create GP-001 with intent, state, scope, expected result.
  3. Object resolver: map obj://sios-root to the actual Fedora path.
  4. Authority: allow only folder.open for that object.
  5. Executor: implement the Fedora-specific folder.open().
  6. Verifier: observe the active file-manager window/path.
  7. Journal: record request → resolution → authorization → execution → verification.
  8. Second primitive: add app.launch and reuse the same path.

13 · POC acceptance suite

How we know the idea actually works

  • Normal Fedora mouse input still works.
  • Hand tracking can move/select without changing GoalProcess code.
  • Voice recording begins only after explicit push-to-talk activation.
  • Releasing push-to-talk cleanly ends the recording and sends audio to local STT.
  • The local controller can map simple commands to allowed SIOS capabilities without executing them directly.
  • Native capabilities are preferred over pixel/pointer automation whenever both are available.
  • An installed MCP capability cannot bypass the same GoalProcess authority checks used by native capabilities.
  • “Open SIOS folder” creates a stable GoalProcess ID.
  • The resolver returns the intended folder object.
  • An unauthorized folder request is denied.
  • folder.open() opens the intended location.
  • The verifier confirms the correct folder is actually visible.
  • If execution fails, the goal does not report COMPLETE.
  • The journal reconstructs the full sequence.
  • Switching from hand input to mouse/keyboard requires no changes to the core control path.

POC success: one user outcome travels end-to-end through Input → GoalProcess → Resolver → Authority → Capability → Fedora → Verifier without depending on one input device or one AI model.

Frozen interaction decision

No wake word in SIOS v0.

Voice interaction is explicitly activated using push-to-talk. Always-listening voice detection, wake-word recognition, and passive microphone activation are postponed until after the core SIOS interaction model has been validated.
